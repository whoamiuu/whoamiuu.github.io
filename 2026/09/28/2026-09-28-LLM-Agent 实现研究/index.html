LLM Agent 实现研究

大语言模型 (Large Language Model，LLM) 通常通过 API 接收用户输入，并返回模型生成的响应。对于普通的对话程序，这个过程通常在获得模型回复后就结束了。

而 Agent 在 LLM 的基础上，通过程序维护对话状态、向模型提供工具定义、处理模型返回的工具调用请求，并根据执行结果继续与模型交互。模型负责生成响应或提出工具调用，宿主程序负责控制执行流程。

一个普通的 Python 程序，怎样变成一个 Agent？

以 deepseek 官方文档提供的 Openai API 格式的访问样例为例，Python 程序需要根据 API 的要求构造 HTTP 请求，其中包括模型名称、对话消息等请求参数，并通过 HTTP 请求头传递 API Key。随后，Python 程序需要接收并解析模型返回的 JSON 数据，从中提取所需的响应内容。

我来写一个简单 Agent ，当然使用第三方 SDK (比如 OpenAI Python SDK) 对开发会更简单，不过我在这里暂时只使用 Python 标准库，以更好理解底层的实现原理。

正如我上面所说，最简 Agent 只需承担构建和解析 HTTP 的作用。换句话说，一个 Python 程序作为 Agent 的基础能力，是构造符合模型 API 规范的 HTTP 请求 (将用户请求、模型ID、API key 等整合成 json 字符串)，以及解析 LLM 返回的 json 消息 (将字节转化为 Python 字典，并提取 message 关键字)。

这个程序的核心任务是完成一次完整的模型请求与响应处理：

  1. 构造请求： 将模型名称、用户输入等参数组织成 Python 字典，再通过 json 模块将其序列化为 JSON，并构造 HTTP 请求。
  2. 发送请求： 使用 urllib.request 向模型 API 发送 HTTP 请求，并读取服务器返回的数据。
  3. 解析响应： 将响应中的 JSON 数据反序列化为 Python 字典，再从中提取模型生成的文本内容。

Agent 怎么实现工具调用？

当然，这个还不算是完整意义上的 Agent，前面实现的程序只能向 LLM 发送请求并获取文本响应，还不具备调用外部工具的能力。接下来，我们将在现有代码的基础上，引入工具调用机制，让模型能够根据用户的任务请求 Python 程序执行相应的函数

首先，我实现两个简单的文件操作工具：read_file() 用于读取文件，write_file() 用于写入文件；为了防止路径穿越，我还添加了一个安全函数 _safe_path()，用于防止路径穿越，避免访问工作目录之外的路径。

工具函数定义完成后，还需要让模型知道有哪些工具可用，以及每个工具的用途和参数要求。

需要注意的是，模型并不需要直接读取 Python 函数的实现代码。Agent 可以通过工具声明向模型提供工具名称、功能描述和参数结构。模型根据这些信息判断是否需要调用工具，并生成相应的工具调用请求；具体的函数执行仍由 Python 程序负责。

这里我使用列表嵌套字典的方式定义工具，并通过 TOOLS 统一管理所有工具的声明。

定义好工具后，Agent 需要在请求模型时提供相应的工具声明，使模型能够根据当前任务选择合适的工具。

在这里，我通过 tools 参数将 TOOLS 传递给 ask_model()，并将其加入 API 请求体。这样，每次调用模型时，模型都能获得当前可用的工具定义。

完成工具函数和工具声明后，接下来实现 Agent 的主循环。

核心逻辑是：Agent 每次向 LLM 发送当前对话历史和可用工具声明，然后根据模型返回的消息决定下一步操作。如果模型返回了工具调用请求，Agent 就执行对应的工具，并将执行结果追加到对话历史中，再次请求模型；如果模型没有返回工具调用请求，则将其文本响应作为本轮任务的最终回答。

在这个过程中，模型可以根据工具执行结果继续生成新的工具调用请求，因此整个过程可能包含多轮模型请求和多次工具执行。

需要注意的是，每次请求模型时，程序都会将当前保存的 messages 发送给模型，其中包括此前的用户消息、模型响应以及工具执行结果。这些消息共同构成当前请求的对话上下文。

上下文窗口指模型在一次请求中能够处理的 Token 总量，并不等同于长期记忆。当前程序只是将对话历史保存在 messages 中，并在后续请求时重新发送；它还没有实现独立的长期记忆机制。

模型返回工具调用请求后，Agent 还需要将请求转换为实际的函数调用。为此，我实现了 run_tool()，负责解析模型返回的工具名称和参数，并调用对应的 Python 函数。

这样一个简单读写文件 Agent 就实现了。

我来添加日志来看 Agent 实际发生了什么。首先观察 Agent 发出的第一次 Request，可以看到，请求中包含系统提示词、用户输入以及 tools 字段中的工具声明。

系统提示词规定了 Agent 的基本行为，用户消息描述了本次任务，而工具声明则向模型提供了可用工具及其参数信息。模型可以结合这些内容，决定是否需要调用工具，以及应该使用哪个工具。

再观察模型返回的 Response，可以看到 choices[0].message 中出现了 tool_calls 字段，表明模型返回了工具调用请求。

其中，外层的 id（例如 488cb4ba-144a-4382-a873-95c9d9526ee9）是本次模型响应的 ID，用于标识这次 API 响应；而 tool_calls 内部的 id（例如 call_00_X6jvQohh9d9Rm8r1p0959169）则用于标识具体的工具调用。

这两个 ID 的用途不同：前者标识模型响应，后者用于将工具执行结果与对应的工具调用关联起来，以便 LLM 在上下文中区分重复的工具调用。

此外，这条响应的 finish_reason 为 tool_calls，表示模型此次响应以工具调用结束，而不是普通的最终文本回答。tool_calls 中的 function.name 指定了要调用的工具，function.arguments 则提供了调用参数。Agent 解析这些字段后，就可以将请求交给本地的工具执行函数处理。

至此，一个具备基本工具调用能力的文件读写 Agent 就实现了。它能够接收用户任务，根据模型生成的工具调用请求执行本地文件操作，并将执行结果反馈给模型，最终生成回答。

通过这个例子，可以看到 Agent 并不是单纯地调用一次 LLM API，而是通过模型响应、工具执行和结果反馈构成一个循环。Python 程序负责控制整个执行流程，LLM 则根据任务和工具返回结果生成后续响应。
